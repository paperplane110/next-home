# Family Tree 2026-07-01 反馈与复盘

date: 2026-07-01

## 1. 目的

记录今天围绕 `family-tree` 页面开发过程中，用户提出的关键改进意见，以及这些反馈暴露出的实现边界、判断失误与后续协作注意点，便于后续复盘 AI 的能力边界。

---

## 2. 今日用户提出的改进意见

### 2.1 交互与体验层

1. 取消“右键新建节点”，仅保留“空白画布双击新建节点”，减少误触。
2. 拖动画布时，不应选中页面上的标题、Drawer、视图切换等文字；需要在拖拽期间临时禁用全局选字。
3. 双击人物节点时，应直接打开编辑抽屉，减少操作步骤。
4. 节点内部的 category 色系不应只是一段 class 字符串，而应抽成可复用的主题对象，便于在 `bg / border / text / badge / ring` 等位置复用。
5. 节点选中时的 `ring` 颜色，应与节点所属 category 保持一致，而不是统一高亮色。
6. 工具栏按钮应抽象为可复用组件，Tooltip 使用统一的 shadcn / Radix UI 方案，不应继续内联在页面里。
7. Tooltip 的弹出方向改为上方后，还需要保证宽度能被内容自然撑开，不能出现过窄问题。
8. Edge 选中后，线条本身可以增强反馈，但 label 不需要跟着高亮。
9. Edge 右键菜单应显示在鼠标右侧，不能离鼠标太远，也不能出现明显偏移。

### 2.2 设计与职责边界

1. Edge 与 Node 的配色对应关系由用户手动维护，AI 不应擅自引入“自动按 category 同步配色”的逻辑。
2. 在 edge 连接规则里，不需要给 `PersonNode` 增加新的 handle 语义；只需根据 source 所在节点类型是否为 `marriageNode` 来判断业务规则。
3. 任务拆解文档不是一次性产物；当用户修改文档后，后续实现必须以用户改过的版本为准，而不是继续沿用旧设计假设。

### 2.3 关系 edge 规则层

1. 删除 marriage edge 时，不应删除其相连的 person node。
2. 一个 person node 连接 marriage node 的场景应被允许，不能被现有连接规则错误拦截。
3. “拖拽新建 edge” 这条链路需要做真正有效的浏览器验证，而不是只停留在静态代码层面的自信判断。
4. 第八项功能在第一轮实现后，仍需要继续覆盖 edge 删除、marriage 规则收紧、保存 / 加载联动等后续工作。

### 2.4 数据与视图一致性层

1. 初始数据节点与新建节点在 `family` 视图中的可见性规则必须一致，不能出现“删除同样的 marriage edge，老节点消失而新节点不消失”的不一致行为。
2. 对“节点看起来被删了”的问题，需要区分：
   - 数据层是否真的从 `graphDraft.nodes` 删除
   - 还是只是 `buildViewGraph()` 过滤后不再显示
3. 需要澄清 `node.position`、`viewMeta.familyTree.position`、`viewMeta.starNetwork.position` 三者的职责，避免后续保存 / 加载时出现“到底该信哪个位置”的歧义。

## 3. 今天暴露出的能力边界

### 3.1 不应主动补充用户未授权的产品规则

本次最典型的问题有两个：

1. 曾尝试把 Edge 和 Node 的颜色建立自动对应关系，但用户明确表示这部分由其手动维护。
2. 曾在 edge 连接规则文档里引入“给 `PersonNode` 增加 marriage 专用 handle”的设计，但用户并不认同这一复杂化方向。

复盘结论：

1. 对于视觉映射、领域语义这类强业务判断，若用户已有明确偏好，AI 不应“自作主张地补完设计”。
2. 在设计文档阶段，优先保持最小语义集，除非用户明确要求，否则不要擅自增加新的交互概念。

### 3.2 不能把“界面消失”误判成“数据被删除”

“删除 marriage edge 后 person node 也没了” 这个问题，第一眼看像删除链路误删节点，但真实原因是：

1. 初始数据节点没有 `views` 字段。
2. `family` 视图的可见性逻辑曾依赖 `node.data.views?.includes("family")`。
3. 删除最后一条 `family` edge 后，这类节点不再命中显示条件，于是只是“从视图中消失”，并不是“从数据里被删掉”。

复盘结论：

1. 以后碰到“对象消失”的问题，要先区分数据态和投影视图。
2. 不能仅凭表象推断为删除逻辑 bug，应该优先检查视图过滤链路。

### 3.3 不能假设静态数据与运行时新建数据结构天然一致

今天另一个关键问题是：

1. 新建节点会写入 `views: ["family", "star"]`。
2. 初始数据人物节点并没有同样的字段。
3. 这导致同一业务操作在“初始节点”和“新建节点”身上表现不同。

复盘结论：

1. 每当运行时创建对象的 schema 与种子数据 schema 不完全一致时，就必须主动排查是否会影响过滤、渲染和保存。
2. 后续如果继续扩展保存 / 加载功能，应尽量把“数据真值字段”收敛到一套稳定结构里。

### 3.4 视觉定位问题不能只微调 offset，必须先确认定位参考系

Edge 右键菜单偏移问题中，`event.clientX / event.clientY` 本身没有错；真正的问题是：

1. 菜单虽然写了 `position: fixed`，
2. 但它渲染在带 `transform` 的祖先层级中，
3. 导致实际定位参考系与预期 viewport 不一致。

复盘结论：

1. 遇到悬浮层偏移问题时，不能先靠“加减 4px / 8px”试错。
2. 应先检查是否受 `transform / filter / contain` 等祖先样式影响。
3. 需要时应直接上 `Portal`，把悬浮层挂到 `document.body`。

### 3.5 需要更早识别“算法位置”和“持久化位置”的差异

今天关于 `position` 的讨论说明，当前模型里其实有三层位置语义：

1. `node.position`：React Flow 运行时渲染位置
2. `viewMeta.familyTree.position`：Family 视图持久化坐标
3. `viewMeta.starNetwork.position`：Star 视图手动坐标覆盖；若缺失，可由 `ring + order` 自动计算

复盘结论：

1. AI 在解释或修改位置逻辑时，不能把所有 `position` 当成同一个概念。
2. 涉及保存 / 加载前，应先明确哪一层才是真正的数据真值。

## 4. 对后续协作的约束建议

1. 若用户已明确说明“某部分由其手动维护”，AI 不再主动扩展这部分逻辑。
2. 若用户已修改任务拆解文档，后续实现一律先回读文档，再开始编码。
3. 当问题表象是“消失 / 偏移 / 不显示”时，优先做分层诊断：
   - 数据是否存在
   - 视图是否过滤
   - 定位参考系是否正确
4. 对多视图页面，新增或删除逻辑完成后，应额外验证：
   - 初始数据节点
   - 新建节点
   - Family / Star 两种视图
5. 在进入保存 / 加载开发前，建议先统一位置字段语义，避免后续 schema 再次分叉。

---

## 5. 今日复盘关键词

- 不要擅自补设计
- 不要混淆数据删除与视图过滤
- 不要默认静态数据与运行时数据完全一致
- 定位问题先看参考系，不先调 magic number
- 多视图图谱的“位置”必须区分运行时与持久化语义
